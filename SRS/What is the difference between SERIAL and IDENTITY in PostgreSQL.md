# What is the difference between SERIAL and IDENTITY in PostgreSQL?

> [!abstract] Short answer
> serial is a PostgreSQL convenience macro: not a real type — it creates an integer column with a DEFAULT of nextval() on an owned sequence, and the column remains an ordinary insertable column. IDENTITY (GENERATED ALWAYS AS IDENTITY, since PostgreSQL 10, SQL standard) builds the same sequence machinery but marks the column as managed: explicit values are rejected unless you say OVERRIDING SYSTEM VALUE, and the column cannot silently diverge from its generator.

## What each expands to

```sql
-- serial is shorthand for:
CREATE TABLE t1 (id integer NOT NULL DEFAULT nextval('t1_id_seq'));
-- identity is the standard feature:
CREATE TABLE t2 (id bigint GENERATED ALWAYS AS IDENTITY);

INSERT INTO t2 (name) VALUES ('a');                          -- ok
INSERT INTO t2 (id, name) OVERRIDING SYSTEM VALUE VALUES (5, 'a');  -- explicit
INSERT INTO t2 (id, name) VALUES (5, 'a');                   -- error
```

**Listing 1.** GENERATED ALWAYS guards the generator; GENERATED BY DEFAULT (the other identity form) behaves closer to serial but is still standard and metadata-visible.

| | serial | identity |
|---|---|---|
| Standard SQL | no (PostgreSQL-ism) | yes (SQL standard) |
| Explicit insert | silently allowed | blocked unless OVERRIDING SYSTEM VALUE |
| Column type | integer/bigint via macro | real column property, any int type |
| Ownership | sequence owned by column | managed by the column |

## Why identity is the modern recommendation

Dump/restore and tooling treat identity columns as first-class properties (ownership, restart, type change in one place); frameworks that INSERT explicit IDs by accident fail loudly instead of corrupting the sequence contract; and schema reviews stop finding "serial columns whose sequence fell behind". Both share sequence behavior: gaps are normal, values never roll back with aborted transactions ([[What are xmin and xmax in PostgreSQL]] — visibility of sequence changes is special).

> [!warning] Neither serial nor identity makes a unique key by itself
> The macro does not add PRIMARY KEY or UNIQUE — a plain serial column accepts duplicates unless you declare the constraint. And sequences have gaps by design: after a rollback or crash, values are consumed forever; do not build business logic on "no holes".

> [!tip] Interview answer
> serial is a shorthand that creates an integer column with a nextval default on an owned sequence — nothing stops explicit inserts, and it is not a real type. GENERATED ALWAYS AS IDENTITY is the SQL-standard, PostgreSQL-10+ feature with the same sequence underneath but system-owned semantics: explicit values need OVERRIDING SYSTEM VALUE. New schemas use identity; both allow gaps by design. If the design goal is keys minted outside the database rather than managed sequences, that is a different trade entirely — [[Should you use UUID as a primary key in PostgreSQL]].
