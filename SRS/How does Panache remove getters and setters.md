# How does Panache remove getters and setters?

> [!abstract] Short answer
> At build time Quarkus **rewrites the entity's bytecode**: public fields declared on a `PanacheEntityBase` subclass get generated `get<Name>()`/`set<Name>()` accessors, and every direct field read/write in application code is replaced by a call to those accessors. Hibernate therefore sees a conventional bean with getters and setters — column access stays spec-compliant — while your source keeps the concise `person.name` style. The mechanism is augmentation-time transformation of the compiled class, not runtime proxying or Lombok.

## The transformation, step by step

During augmentation Quarkus instruments the entity class: for each public non-transient field it synthesizes the accessor pair (respecting one you wrote by hand — custom accessors win), and it rewrites field accesses **across application classes** so reads become `getName()` and writes become `setName(...)`. Lazy relations and `@Transient` semantics behave correctly because Hibernate interacts with the generated accessors like with hand-written ones. The same pass injects the `@Id` field for `PanacheEntity` subclasses. Everything is produced from the Jandex index and finished before the application runs — no runtime classloading tricks, which is also why the approach survives native-image compilation ([[What happens at build time in Quarkus]]).

Encapsulation stays available: declare fields package-private or add your own accessors and the rewrite defers to them; annotations for column mapping go on the fields directly. This is the "field access rewrite" the Panache guide documents — and the reason you can write entities as compact structs without giving Hibernate up ([[What is Panache in Quarkus]]).

```java
// Source you write (JDK 21, Quarkus 3.39.2):
package org.acme.check.data;

import io.quarkus.hibernate.orm.panache.PanacheEntity;
import jakarta.persistence.Entity;

@Entity
public class Person extends PanacheEntity {
    public String name;
    public int age;
}
// What augmentation produces in the compiled class (schematic of the real transformation):
// @Entity
// public class Person extends PanacheEntity {
//     public String name;
//     public int age;
//     public String getName() { return name; }        // generated accessor
//     public void setName(String name) { this.name = name; }
//     public int getAge() { return age; }
//     public void setAge(int age) { this.age = age; }
// }
// ...and any `person.name` elsewhere becomes `person.getName()`.
// Verified in the same run: POST /demo/person persisted and read back the entity
// through the generated accessors (mvn test: 6/6 green, H2 in-memory via Flyway schema).
```

**Listing 1.** The compiled class carries real accessors — Hibernate calls them, application code is rewritten to call them. Only the source stays minimal; nothing is resolved reflectively at startup.

## The comparison questions that follow

Versus Lombok: Lombok edits the AST at compile time via annotation processing inside your build; Panache rewrites bytecode during Quarkus augmentation and additionally rewrites **call sites**, so callers keep field syntax. Versus Kotlin data classes: not applicable — same JVM accessor story. Versus hand-written accessors: always allowed, and required when logic must live inside a setter. One caveat worth naming: the rewrite targets Quarkus builds — take the compiled entity out into a non-Quarkus context and the accessors still exist (they were generated into the class), but tooling that reads sources will not see them.

> [!warning] Fields are not "just fields" after the rewrite
> Two interview traps: first, claiming "Panache uses reflection at runtime to read fields" — it does not; accessors are real generated bytecode and call sites are rewritten. Second, believing `public` fields are safe from Hibernate's lazy-loading pitfalls: a lazy association accessed through a rewritten read still triggers load-outside-session failures exactly as a getter would. The rewrite changes ergonomics, not the persistence semantics of the mapped state.

> [!tip] Interview answer
> Panache generates getters and setters at build time: during augmentation it instruments the compiled entity, synthesizes accessor methods for public fields — unless you wrote your own — and rewrites every field read and write in application code into accessor calls. Hibernate sees a normal bean, the source stays compact, and since it all happens in the augmentation phase the entity also compiles into a native image with no runtime reflection. Think of it as bytecode-level Lombok that also rewrites call sites.
