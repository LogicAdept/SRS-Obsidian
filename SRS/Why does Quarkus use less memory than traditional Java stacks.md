# Why does Quarkus use less memory than traditional Java stacks?

> [!abstract] Short answer
> Memory savings come from removing work and classes from the runtime, not from a magic flag: **build-time augmentation** means no discovery machinery, annotation parsers or framework metadata caches at runtime; **fewer classes are loaded** (recorded bytecode replaces generic engines); **lazy client proxies** avoid instantiating unused beans; generated code replaces reflection-driven dispatch; and in native mode the whole JVM heap machinery is absent, with only reachable code in the image. JVM-mode RSS is correspondingly smaller; native RSS is smaller again by an order of magnitude.

## Where the bytes actually go

A traditional framework at startup loads thousands of classes to *discover* what to build — classpath scanning, reflection metadata, proxy classes, XML/annotation parsing caches — and keeps most of it resident. Quarkus pays that cost during augmentation, ships only the result (recorded bootstrap in the generated bytecode jar), and the runtime loads the small runtime-side artifacts of each extension plus your classes ([[What happens at build time in Quarkus]]). Bean instances: normal-scoped beans are lazy behind client proxies, unused beans are removed at build (`quarkus.arc.remove-unused-beans`), so the live object graph matches what the application really uses ([[What bean scopes does Quarkus support]]). Thread counts matter too: a handful of event-loop threads plus a modest worker pool replaces per-request thread stacks of blocking stacks ([[How does Quarkus decide which thread runs your code]]) — thread stacks are RSS. Native mode removes the JVM baseline (metaspace, JIT compiler arenas, default heap growth): the image holds only reachable code and data, and startup allocates from a fixed layout.

## How to answer with numbers honestly

Interviewers often push for figures. The safe form: "on our service, moving to fast-jar JVM mode cut RSS by a visible margin and native cut it to a fraction of that — but the multiplier depends on the app, JDK, GC settings and traffic; the mechanisms above are why the direction is reliable." Quoting one universal number ("10x less memory") is a junior tell, because heap settings dominate JVM-mode RSS and application shape dominates native.

> [!warning] Low RSS is not low heap obligation
> JVM-mode Quarkus respects `-Xmx`/`-Xms` like any Java app — a default-generational heap absorbs the savings instantly; container-fit memory claims require explicit heap sizing (percentage-based `MaxRAMPercentage`, modest `-Xmx`) plus awareness that metaspace, code cache and thread stacks are outside the heap. The mirrored myth: "build-time config means zero runtime memory for config" — config objects still exist; what is gone is the *discovery* cost, not the state. And Dev Services/dev mode are irrelevant to prod memory: they are development-time conveniences.

> [!tip] Interview answer
> Quarkus' memory advantage is architectural: augmentation moved discovery, metadata parsing and code generation to build time, so the runtime loads fewer classes and holds no framework caches; ArC removes unused beans and normal-scoped beans instantiate lazily behind proxies; the event-loop model keeps thread counts low, and thread stacks are RSS. Native mode removes the JVM baseline entirely, keeping only reachable code. I avoid quoting magic multiples — the direction is reliable, the number depends on heap config and application shape.
