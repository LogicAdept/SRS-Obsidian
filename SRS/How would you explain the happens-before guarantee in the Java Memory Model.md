# How would you explain the happens-before guarantee in the Java Memory Model

> [!abstract] Short answer
> **Happens-before is the JMM's visibility contract: if action A happens-before action B, then A's effects are visible to B and ordered before it.** The edges come from program order within a thread and from synchronization actions across threads — volatile write→read, monitor unlock→lock, `start()`, `join()`, interrupt — closed transitively.

## The rule list (JLS 17.4.4-17.4.5)

The relation `hb(A, B)` is generated by program order plus the synchronizes-with edges, closed under transitivity. One card per rule:

- **Program order** — actions of the same thread in source order ([[What is the program order rule in the Java Memory Model]]).
- **Monitor** — an unlock happens-before every subsequent lock of the same monitor ([[What is the monitor lock rule in the Java Memory Model]]).
- **Volatile** — a write to a `volatile` field happens-before every subsequent read of that field ([[What is the volatile visibility rule in the Java Memory Model]]).
- **Start** — `start()` happens-before any action in the started thread ([[What is the thread start rule in the Java Memory Model]]).
- **Termination** — all actions of a thread happen-before a `join()`/`isAlive()` that detects its termination ([[What is the thread termination rule in the Java Memory Model]]).
- **Interrupt** — an interrupt happens-before the point where the interruption is detected ([[What is the interrupt happens-before rule in the Java Memory Model]]).
- **Default value** — the default write to each variable happens-before the first action in every thread ([[What is the default value happens-before rule in the Java Memory Model]]).
- **Finalizer** — the end of a constructor happens-before the start of that object's finalizer ([[What is the finalizer happens-before rule in Java]]).
- **Class initialization** — static initializers run before the first use of the class, under the initialization lock ([[What does class initialization guarantee about static field visibility in Java]]).
- **Synchronizes-with** — the cross-thread edges themselves form the raw edge set ([[What is the synchronizes-with relation in the Java Memory Model]]).
- **Transitivity** — `hb(A, B)` and `hb(B, C)` give `hb(A, C)`, composing chains across threads ([[What is the transitivity of happens-before in the Java Memory Model]]).

The java.util.concurrent packages extend the same guarantees to higher-level tools, one property per tool: concurrent collections ([[What memory consistency do concurrent collections guarantee in Java]]), executor submission ([[What memory consistency does executor submission guarantee in Java]]), `Future.get` ([[What memory consistency does Future get guarantee in Java]]), synchronizer release/acquire ([[What memory consistency do synchronizer release and acquire guarantee in Java]]), barriers ([[What memory consistency do barrier synchronizers guarantee in Java]]), `Exchanger` ([[What memory consistency does Exchanger exchange guarantee in Java]]), atomic read-modify-write operations ([[What memory effects do atomic operations have in Java]]), and VarHandle access modes ([[How do VarHandle access modes order memory in Java]]). Two umbrella cards frame the whole model: the DRF-SC guarantee for correctly synchronized programs ([[What does the Java Memory Model guarantee for data race free programs]]) and the allowed-reads regime that takes over once a data race exists ([[What reads does the Java Memory Model allow in a data race]]).

```java
// writer thread
data = 42;

// reader thread
if (ready) {

}
```

**Listing 1.** The message-flag idiom. The read of `data` cannot observe 0 once `ready` is seen — a 2 000-iteration stress run on JDK 21 printed `stale 0 out of 2000`.

> [!warning] Happens-before is not a timestamp and not mutual exclusion
> The spec itself warns: an happens-before relation between two actions does NOT mean they execute in that order in the implementation — reordering is fine while results stay consistent, so "happens-before" reads better as "is visible before". Three follow-on traps. One: HB is pairwise and field-specific — a volatile flag makes only writes *before it* visible; a write issued after the volatile store rides outside the edge. Two: HB never makes compound actions atomic — a `volatile int` still loses increments ([[Why is the Java increment operator not atomic]]); atomicity needs CAS (`AtomicInteger`) or a monitor ([[How would you explain the volatile field modifier in Java]]). Three: without any edge there is no guarantee at all — a read may see the default value even if the write "obviously" happened first in real time; that is precisely the definition of a data race ([[What is the difference between a race condition and a data race]]) and the visibility story behind [[What is memory visibility in the Java Memory Model]] and [[How does the Java Memory Model define visibility and ordering]].

> [!tip] Interview answer
> **Happens-before is the transitive visibility relation of the JMM: program order inside a thread, plus synchronizes-with edges — volatile write before its subsequent read, monitor unlock before the next lock, start before the thread, thread actions before join. If A happens-before B, A's write is guaranteed visible at B. It orders visibility, not clock time, and it is not atomicity — compound actions still need CAS or locks.**
