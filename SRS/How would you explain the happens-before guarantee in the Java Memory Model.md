# How would you explain the happens-before guarantee in the Java Memory Model

> [!abstract] Short answer
> **Happens-before is the JMM's visibility contract: if action A happens-before action B, then A's effects are visible to B and ordered before it.** The edges come from program order within a thread and from synchronization actions across threads — volatile write→read, monitor unlock→lock, `start()`, `join()`, interrupt — closed transitively.

## The rule list (JLS 17.4.5)

The relation `hb(A, B)` is generated by exactly these edges:

- **Program order** — actions in the same thread in source order.
- **Monitor** — an unlock happens-before every subsequent lock of the same monitor.
- **Volatile** — a write to a `volatile` field happens-before every subsequent read of that field.
- **Thread lifecycle** — `start()` happens-before any action in the started thread; every action in a thread happens-before a `join()`/`isAlive()` that detects its termination; `interrupt` happens-before the point where interruption is detected.
- **Transitivity** — `hb(A, B)` and `hb(B, C)` give `hb(A, C)`.

```java
static int data;
static volatile boolean ready;

// writer thread
data = 42;
ready = true;

// reader thread
if (ready) {
    int v = data;   // guaranteed 42
}
```

**Listing 1.** The message-flag idiom. The read of `data` cannot observe 0 once `ready` is seen — a 2 000-iteration stress run on JDK 21 printed `stale 0 out of 2000`.

> [!warning] Happens-before is not a timestamp and not mutual exclusion
> The spec itself warns: an happens-before relation between two actions does NOT mean they execute in that order in the implementation — reordering is fine while results stay consistent, so "happens-before" reads better as "is visible before". Three follow-on traps. One: HB is pairwise and field-specific — a volatile flag makes only writes *before it* visible; a write issued after the volatile store rides outside the edge. Two: HB never makes compound actions atomic — a `volatile int` still loses increments ([[Why is the Java increment operator not atomic]]); atomicity needs CAS (`AtomicInteger`) or a monitor ([[How would you explain the volatile field modifier in Java]]). Three: without any edge there is no guarantee at all — a read may see the default value even if the write "obviously" happened first in real time; that is precisely the definition of a data race ([[What is the difference between a race condition and a data race]]) and the visibility story behind [[What is memory visibility in the Java Memory Model]] and [[How does the Java Memory Model define visibility and ordering]].

> [!tip] Interview answer
> **Happens-before is the transitive visibility relation of the JMM: program order inside a thread, plus synchronizes-with edges — volatile write before its subsequent read, monitor unlock before the next lock, start before the thread, thread actions before join. If A happens-before B, A's write is guaranteed visible at B. It orders visibility, not clock time, and it is not atomicity — compound actions still need CAS or locks.**
