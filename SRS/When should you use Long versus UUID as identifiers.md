# When should you use Long versus UUID as identifiers

> [!abstract] Short answer
> Use an auto-increment Long when a single database owns ID generation and internal compactness matters: 8 bytes versus 16, sequential inserts that append to B-tree pages, readable URLs. Use UUIDs when identifiers are generated by many independent nodes (offline clients, microservices, pre-allocating IDs before commit) or when you must not expose business volume; prefer time-ordered UUIDv7 (or Snowflake-style IDs) to avoid random-insert page splits. A common hybrid: UUID for external references, Long inside the database.

## The Long side

A 64-bit auto-increment key is the default for a reason: it is half the size of a UUID, every secondary index stores the same key so the saving multiplies across indexes, and monotonic values always insert into the rightmost B-tree page — dense pages, small write amplification, cheap page fills. Sequence gaps and per-shard coordination are the costs: a single sequence is a central generator, so sharded or offline generation needs ranges or different IDs entirely. Sequential IDs also leak information — an /orders/12345 URL reveals the order count, and enumerating neighbors is trivial — which is why public APIs often map internal Longs to external opaque tokens. The GUID question ("is a GUID good practice") is the same tradeoff asked from the other side, and the comparison below is its substance.

## The UUID side

UUIDs need no coordination: any node generates a globally unique ID before the row exists, which unblocks offline clients, parallel importers, and services that each insert into their own shard. Random UUIDv4 values, however, scatter inserts across the whole B-tree: pages split before filling, the buffer cache holds a much larger working set, and every index inherits the 16-byte key. Time-ordered UUIDv7 keeps the coordination-free property while making values roughly monotonic, recovering append-friendly inserts — the same idea as Snowflake-style 64-bit time-plus-shard-plus-sequence IDs. [[How would you explain what a primary key is in relational databases]] fixes the requirements any choice must satisfy, and [[What is a database index and why does it speed up queries]] explains why insertion order dominates index health.

```text
Long (8B): 1,2,3,...         -> append to last B-tree page (dense)
UUIDv4 (16B): random         -> insert anywhere (page splits, fragmentation)
UUIDv7 (16B): time-ordered   -> mostly append, still 2x key size
rule of thumb: single-writer + internal -> Long
               multi-writer / external -> UUIDv7 or Snowflake-style
```

> [!warning] Random UUIDs on a hot table are a silent performance tax
> UUIDv4 primary keys work fine in dev and degrade as the table and its indexes grow: page splits, a bloated buffer-cache working set, and bigger every secondary index. The fix is versioned — UUIDv7 or a snowflake scheme — not just "add caching".

> [!tip] Interview answer
> Long wins on size, B-tree locality and readability when one database generates IDs; UUID wins when many nodes must generate IDs independently or the identifier must be opaque. Random UUIDv4 fragments indexes, so for distributed generation I pick time-ordered UUIDv7 or a snowflake ID — or the hybrid: Long inside, UUID at the API edge.
