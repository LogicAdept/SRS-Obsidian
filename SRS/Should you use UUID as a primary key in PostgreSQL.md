# Should you use UUID as a primary key in PostgreSQL?

> [!abstract] Short answer
> It depends on the requirement for offline uniqueness. UUIDs (16 bytes) let different systems generate keys without coordination — the right tool for distributed generation and for exposing IDs publicly. The costs: every foreign key and every index doubles key width versus bigint, and random UUIDv4 values destroy B-tree locality, so insert-heavy tables bloat their indexes. PostgreSQL 18 added native UUIDv7 generation, whose time-ordered values fix most of the locality cost.

## The trade

| | bigint identity | UUIDv4 | UUIDv7 |
|---|---|---|---|
| Size | 8 bytes | 16 bytes | 16 bytes |
| Generated by | one database | anyone, anywhere | anyone, anywhere |
| Index locality | perfect (monotonic) | none (random) | time-ordered |
| Safe to expose | leaks volume | yes | yes (leaks time) |

```sql
CREATE TABLE events (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid()   -- v4, built-in since PG 13
);
-- PostgreSQL 18:
SELECT uuidv7();   -- time-ordered: better index locality
```

**Listing 1.** Random v4 is the common default; v7 sorts roughly by creation time, keeping B-tree inserts right-packed like a sequence ([[What is the difference between SERIAL and IDENTITY in PostgreSQL]] covers the bigint generation side).

## When UUIDs earn their cost

- Keys minted by multiple services, mobile clients, or during merges where a central sequence is unavailable.
- IDs travel in URLs and APIs; unguessable and volume-hiding values are a plus ([[Is a primary key implemented as an index and why]] — the PK is an index, so key width multiplies into every referencing FK index too).
- Multi-master or logical-replication topologies where sequence ranges collide ([[What is the difference between streaming and logical replication in PostgreSQL]]).

## When bigint wins

Pure single-database OLTP with no offline minting: narrower keys mean smaller PK, smaller FK columns and indexes, better cache hit ratios, faster joins. At scale the difference is measurable, not academic.

> [!warning] "UUID v4 as PK is free" and "never use UUIDs" are both lies
> The real variables are key width times index count and insert locality. A UUIDv4 PK on a write-hot table with three FK children pays four times; a UUIDv7 PK on an insert-mostly table pays far less. And bigint leaks business volume the moment an ID appears in a URL — sometimes that alone decides for UUID.

> [!tip] Interview answer
> UUIDs buy decentralized, safe-to-expose identity at the price of 16-byte keys and, for random v4, terrible B-tree locality on inserts. Default to bigint identity inside one database; choose UUID when keys must be minted independently, and prefer time-ordered v7 (native in PostgreSQL 18) or ULID-style values to keep index inserts ordered.
