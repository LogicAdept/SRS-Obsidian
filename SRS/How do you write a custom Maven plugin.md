# How do you write a custom Maven plugin

> [!abstract] Short answer
> **Create a project with `packaging` set to `maven-plugin`, write one class per goal that extends `AbstractMojo`, annotate it with `@Mojo(name = ...)`, and put logic in `execute()`.** The maven-plugin-plugin scans annotated classes, generates the plugin descriptor into the jar, and the build picks a command-line prefix from the artifact name; parameters are annotated fields mapped from the POM or `-D` properties.

A goal implementation is called a Mojo (a play on POJO — "Maven plain Old Java object"). Each annotated class becomes one goal; a plugin is just a jar distributing related Mojos. The plugin tools only include classes carrying the `@Mojo` annotation into the generated descriptor, so an unannotated class is silently not a goal.

## Minimal mojo and its project

```java
package sample.plugin;

import org.apache.maven.plugin.AbstractMojo;
import org.apache.maven.plugin.MojoExecutionException;
import org.apache.maven.plugins.annotations.LifecyclePhase;
import org.apache.maven.plugins.annotations.Mojo;
import org.apache.maven.plugins.annotations.Parameter;
import org.apache.maven.plugins.annotations.ResolutionScope;

@Mojo(name = "sayhi", defaultPhase = LifecyclePhase.PROCESS_SOURCES,
      requiresDependencyResolution = ResolutionScope.COMPILE)
public class GreetingMojo extends AbstractMojo {

    @Parameter(property = "sayhi.greeting", defaultValue = "Hello World!")
    private String greeting;

    @Override
    public void execute() throws MojoExecutionException {
        getLog().info("Greeting: " + greeting);
    }
}
```

**Listing 1.** The canonical shape: `AbstractMojo` supplies logging and infrastructure, the mojo itself only fills `execute()`.

```xml
<groupId>sample.plugin</groupId>
<artifactId>hello-maven-plugin</artifactId>
<version>1.0-SNAPSHOT</version>
<packaging>maven-plugin</packaging>

<dependencies>
  <dependency>
    <groupId>org.apache.maven</groupId>
    <artifactId>maven-plugin-api</artifactId>
    <version>3.9.9</version>
    <scope>provided</scope>
  </dependency>
  <dependency>
    <groupId>org.apache.maven.plugin-tools</groupId>
    <artifactId>maven-plugin-annotations</artifactId>
    <scope>provided</scope>
  </dependency>
</dependencies>
```

**Listing 2.** The plugin project in one view: `maven-plugin` packaging plus two `provided` dependencies — the API at compile time, Maven supplying both at runtime.

The `@Parameter` fields are wired from the POM's `<configuration>` element (element name = field name), from a `-Dsayhi.greeting=...` command-line property, or from the `defaultValue` — which may itself be an expression like `${project.version}` injected from the build context. `@Mojo` attributes control runtime placement: `defaultPhase` binds the goal without an explicit `<execution>`, `requiresDependencyResolution` asks Maven to populate the classpath scope the mojo needs, `threadSafe` declares the goal safe to run in parallel builds. Failing loudly is a choice of exception: `MojoExecutionException` aborts with a **BUILD ERROR** (something unexpected broke), `MojoFailureException` with a **BUILD FAILURE** (an anticipated check did not pass — the same distinction Surefire uses for test failures, [[What is the difference between the Surefire and Failsafe plugins in Maven]]).

The artifact name doubles as the command-line name: `hello-maven-plugin` gives the prefix `hello`, so the goal runs as `mvn hello:sayhi` — [[What are Maven plugins and how are goals invoked]] covers the prefix mapping. To run the goal inside the build instead of ad hoc, bind it with an `<execution>` ([[How do you bind a plugin goal to a lifecycle phase in Maven]]). For scaffolding, the official mojo archetype generates the whole project: `mvn archetype:generate -DarchetypeArtifactId=maven-archetype-plugin` ([[What is a Maven archetype]]).

> [!warning] Naming and descriptor traps
> The `maven-<prefix>-plugin` name pattern is reserved for Apache's own plugins — a third-party plugin must be `<prefix>-maven-plugin`. And since the descriptor is generated from annotations at build time, a mojo added but never annotated compiles fine and then simply does not exist for Maven: the error surfaces later as "no plugin found for prefix" or "unknown goal".

> [!tip] Interview answer
> **A custom plugin is a `maven-plugin`-packaged project where each goal is an `AbstractMojo` subclass annotated `@Mojo`; parameters come in through annotated fields (`property` for `-D`, `defaultValue` with expressions), the descriptor is generated by maven-plugin-plugin, and the artifact name provides the `hello:sayhi` prefix. Failures are signaled by throwing `MojoExecutionException` for errors or `MojoFailureException` for anticipated failures.**
